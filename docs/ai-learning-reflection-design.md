# AI学習リフレクション 設計・解析書

この文書は、現在のMetaWatch実装をコードから確認した内容と、将来の改善案を分けて記録します。仕様の説明は実装とテストで確認できる範囲に限ります。

## 1. 概要とAPIキー設定

AI学習リフレクションは、日次振り返りと当日の学習計画をOpenAIへ送り、次の3項目を日本語で生成する機能です。

- A. 昨日の振り返り
- B. 過去の記録から見えること
- C. 今日の学習に向けて

**APIキーの入力欄はAI学習リフレクション欄にあります。** `type=password` の入力欄から保存・削除できます。入力後に保存しても値は再表示せず、画面の状態APIは設定済みか、保存元がどれかだけを返します。

画面から保存したキーは、リポジトリやSQLiteデータベースの外にある、アプリ専用のローカル設定ファイルへ保存します。

```text
~/Library/Application Support/MetaWatch/openai-key.json
```

保存時は `MetaWatch` ディレクトリを0700、ファイルを0600にし、一時ファイルへ書いてからアトミックに置き換えます。設定ファイルは暗号化されないJSONです。同じOSユーザーとして動くプロセスには読めるため、OSユーザーアカウント、端末、バックアップを保護してください。ディレクトリまたはファイルへ安全にアクセスできない場合、保存・読込エラーを状態画面に表示し、キー設定エラー中は分析を実行しません。

既存利用者向けに環境変数 `OPENAI_API_KEY` もサポートします。**ローカル設定ファイルのキーを優先し、ファイルにキーがない場合だけ環境変数へフォールバック**します。ローカルキーを削除すると、環境変数が存在すればそちらへ切り替わります。環境変数だけのキーは画面から削除できず、起動元の環境設定から削除する必要があります。設定ファイルが壊れている場合は環境変数へ黙って切り替えず、問題を表示します。既定モデルは `gpt-4o-mini` で、必要に応じ `OPENAI_MODEL` で変更できます。

キー値をURL、ソースコード、README、ブラウザー応答、SQLite、エクスポート、HTTPアクセスログに含めない設計です。キーは同一オリジンのPOST本文でローカルサーバーへ送られ、ブラウザーからOpenAIへ直接送信されません。READMEの「AI学習リフレクション」にも設定方法があります。

## 2. 利用者の同意と画面動作

初回は、送信する記録の種類と自動分析・料金発生の可能性を表示したチェックボックスに同意するまで、分析を有効化しません。同意はSQLiteに記録されます。同意を取り消すと同意レコードを削除し、その後の分析API要求は拒否されます。過去に保存された分析結果は自動では削除されず、既存結果は状態表示の対象です。

同意済みでも、サーバー側のキーまたは分析対象記録がなければOpenAIへは送信しません。画面では「昨日の記録なし」と「直近14日間の分析対象なし」を別々に表示します。対象日の前日に記録がなくても、それ以前の対象期間に記録があれば分析できます。

自動分析はメインページの状態取得後、同意・キーがあり、当日の自動確認が未完了で、処理中でなく、成功結果がないときに自動APIエンドポイントへ要求されます。対象記録が0件かどうかはサーバーが再確認し、0件ならOpenAIへ送信せず終了します。同日の再訪では保存済み結果を使います。記録や計画が変わって結果が古くなっても自動再分析はせず、手動再分析ボタンを表示します。手動再分析の直前には、記録を再送信し追加料金が発生する可能性を確認します。

## 3. データベース

初期化時に、既存データを置き換えず次のテーブルと索引を追加します（`app.py` の `init()`）。

| テーブル | 保存内容 |
|---|---|
| `ai_reflection_consent` | ID固定の同意レコードと同意日時。撤回時はこの行を削除。 |
| `ai_reflection_daily_state` | `target_date` ごとの `auto_count`（0または1）、`auto_checked`、確認日時。 |
| `ai_reflection_runs` | 実行日、`auto`/`manual`、状態、要求・生成日時、対象record ID一覧、入力SHA-256、モデル、prompt version、JSON結果またはエラー。 |

`ai_reflection_one_auto_per_date` は日付ごとの自動実行を一意にし、`ai_reflection_one_generation_per_date` は同じ日付に処理中のrunが複数できるのを防ぎます。制限と結果はSQLiteに残るので、通常のプロセス再起動後も維持されます。これらのAIテーブルは既存の講座・単元・振り返りデータを変更しません。

## 4. 分析入力とstale判定

日付は固定UTC+09:00で求めます。対象期間は対象日を含む14日間（対象日から13日前〜対象日）です。対象期間内の `daily_reflections` と、対象日の `study_plans` を取得します。日次振り返りがある日だけを入力に含め、空白日を否定的に評価しないようモデルへ指示します。

OpenAIへ送るJSONは次の情報です。

- 対象日、期間開始・終了日、昨日の日付
- 各日次振り返りの記録日、計画達成、学習時間（分）、自己評価、改善点、明日の計画、記録日時
- 対象日の学習計画に含まれる講座名と単元名

**内部record IDはOpenAI送信ペイロードに含めません。** IDはrunの `record_ids_json` と入力ハッシュ用にSQLiteへ保存します。入力ハッシュは送信JSON相当の内容と対象ID一覧を、キー順を固定したJSONにしてSHA-256で計算します。

状態取得時に現在の入力ハッシュと、直近の成功runに保存したハッシュを比較します。不一致なら `stale=true` として既存結果を保持したまま古い結果と表示します。記録の編集・追加・削除そのものではOpenAI要求を起こしません。

## 5. OpenAI要求と結果検証

サーバーはPython標準ライブラリ `urllib` で `https://api.openai.com/v1/chat/completions` にPOSTします。認証ヘッダーはローカル設定ファイルを優先し、なければ環境変数から取得したBearerキーです。タイムアウトは30秒、読み込む応答の上限は100,000 bytesです。リダイレクト等の追加APIクライアント機能は導入していません。

要求はJSON Schemaモードを指定し、次の文字列フィールドを必須にします。追加プロパティは許可しません。

```json
{
  "yesterday_reflection": "string",
  "past_observations": "string",
  "today_suggestions": "string"
}
```

受信後もJSON形式、キーの集合、値の型、空文字でないこと、各値4,000文字以下を検証します。正常結果はJSONとして `ai_reflection_runs.result_json` に保存します。

システム指示では、入力記録だけを根拠にすること、記録日時を根拠として示すこと、自己評価を能力の証明と混同しないこと、記録にない成果を推測しないこと、根拠の乏しい傾向を作らないことを指定します。これらはモデルへの指示であり、出力内容の正確性を保証するものではありません。

## 6. 実行制御・状態遷移

自動・手動どちらも、要求前にSQLiteで `BEGIN IMMEDIATE` を開始し、同意、キー、対象記録、日別状態、処理中runを確認します。自動要求ではAPI要求を始める前に当日分の `auto_count=1` と `auto_checked=1` を保存し、`generating` runを登録します。その後、ネットワーク要求をトランザクション外で実行します。

```text
未確認
  ├─ 同意なし → 拒否（403）
  ├─ キーなし → 拒否（503）
  ├─ 対象記録なし → no_records（API要求なし）
  ├─ 当日自動確認済み → already_checked（API要求なし）
  ├─ 同日処理中 → 競合（409）
  └─ 自動/手動要求 → generating
       ├─ 成功 → succeeded、結果を保存
       └─ 通信/API/応答検証エラー → failed、エラーを保存
```

- 自動実行は対象日ごとに最大1回です。失敗しても自動再試行しません。記録が0件の場合は、自動実行でその日の確認済み状態を記録し、その後同日に記録が追加されても自動送信しません。
- 同一日付の過去成功がある場合、自動実行は保存済み結果を優先し、同日2回目の自動要求をしません。
- 手動再分析は自動カウントを増やしませんが、明示的な操作ごとに追加のAPI要求になり得ます。手動実行の回数自体にはアプリ内上限を設けていません。
- 同一日付の自動/手動を問わず、処理中runがあれば新しいrunは開始せず409を返します。`BEGIN IMMEDIATE` と一意索引で同時タブからの二重自動要求を抑制します。
- 失敗runは記録されますが、直前の成功結果を上書き・削除しません。最新成功結果と最新失敗エラーを別々に読み、両方表示できます。
- 翌日の対象日は別の日別状態となり、自動1回枠が新しくなります。

**実装上の注意:** 自動実行では呼び出し前に上限を消費します。よって通信失敗でも当日の自動枠は戻らず、再試行は手動操作に限られます。また、プロセスが `generating` 登録後、完了状態を書き込む前に異常終了した場合のrun回収・タイムアウト失効処理は現在ありません。処理中runの一意索引が残るため、同じ対象日の新規runを妨げる可能性があります。

## 7. キー設定・未同意・対象なし・エラー時

| 状態 | 現在の挙動 |
|---|---|
| 未同意 | UIは未生成状態と同意内容を表示。実行APIは403で拒否。 |
| キー未設定 | 未設定と保存元を表示し、実行APIは503で拒否。キー値はブラウザー応答へ含めない。 |
| ローカル設定と環境変数の両方あり | ローカル設定ファイルを使用。削除確認には環境変数へ切り替わることを表示。 |
| 環境変数のみ | 環境変数を使用し、そのキーは画面から削除できないと表示。 |
| 設定ファイルが不正・読込不可 | エラー状態を表示し、環境変数へは自動フォールバックしない。キー更新またはファイル削除で復旧可能。 |
| 環境変数が不正 | ローカルキーがあればそのキーを利用し、なければ設定エラーを表示して送信を行わない。 |
| 設定フォルダー/書込エラー | エラーを明示して保存を拒否。キー値は応答やエラー文に含めない。 |
| 直近14日の日次記録0件 | 状態と「対象なし」を表示。生成APIは `no_records` を返し、OpenAIへ送らない。 |
| 昨日の記録なし、過去記録あり | 昨日の記録なしを明示しつつ、存在する期間内記録を対象にできる。 |
| 同日処理中 | 409を返す。UIの状態取得では処理中runを表示。 |
| OpenAI HTTP/接続/タイムアウト/応答検証エラー | 失敗runとエラーを記録し、自動再試行しない。直近成功結果は保持。手動再分析は別途可能。 |
| 入力が保存済み結果から変化 | stale表示。変更を契機にしたAPI要求は行わない。手動再分析のみ可能。 |

## 8. プライバシーと運用

送信される文章には、改善点・明日の計画・講座名・単元名など利用者が入力した内容が含まれます。同意前に対象内容をUIで説明します。OpenAI利用料金が発生し得ること、特に手動再分析は追加要求であることも表示します。OpenAI側でのデータ保持・利用条件はこのアプリのコードでは制御しないため、利用前にOpenAIの契約・プライバシー条件を確認してください。

キーの通常の設定先はアプリ専用ローカル設定ファイルです。これはアクセス権を絞った平文JSONで、暗号化やOSキーチェーン保護ではありません。ファイルを読める同じユーザー権限のプロセス、または端末の管理者から秘密を保護するものではありません。環境変数も従来どおり利用できます。キー自体はHTTP応答・URL・アプリのSQLite・エクスポート・HTTPアクセスログへ記録しません。設定ファイルを削除すると通常のファイル削除を行いますが、ストレージ上のデータを物理的に消去できる保証はありません。アプリはローカル利用向けで認証機能を持たないため、端末・ユーザーアカウントへのアクセスを保護してください。SQLiteバックアップには同意状態と分析結果が含まれます。OSレベルのバックアップにローカル設定ファイルが含まれる可能性にも注意してください。

## 9. テスト・検証状況

現在のテストコード（`test_app.py`）で確認している事項:

- アプリ画面からのキー保存、0600ファイル/0700親フォルダー、初期化後の再読込、設定削除
- 状態APIがキー値を返さないこと、ローカルキー優先と環境変数フォールバック、および削除後の環境変数への切替
- 不正JSON・読込/書込エラーの明示、同一オリジン制約、キー値がURL・応答・アクセスログ・SQLite・エクスポートに含まれないこと
- 同意なし、キーなし、対象記録なしではOpenAI関数を呼ばないこと
- 14日境界、昨日の記録有無、送信ペイロードに内部IDを含めないこと
- 同時アクセスによる自動要求のsingle-flightと日別カウント1回
- DB初期化を再実行しても結果と日次制限が残ること
- 記録追加後のstale表示、自動枠維持、手動再分析、翌日の新しい枠
- API失敗時に直近成功結果が保持され、自動再試行しないこと
- OpenAI要求のモデル・サーバー認証ヘッダー・JSON Schema、応答形式検証

この文書のキー設定対応を含む最新検証では `python3 -m unittest -q` が46件成功し、`python3 -m py_compile app.py test_app.py` と `git diff --check` も成功しました。ブラウザーの狭幅表示でキー値を再表示しないこと、パスワード入力、保存後の入力欄クリア、ローカル保存元の表示、確認後の削除と未設定への復帰を確認しました。実キー・OpenAI API通信は使用していません。

**未確認:** 有効なAPIキーを使ったOpenAI実通信、実課金、OpenAI側での実際の応答品質や保持条件。API通信自体はモックで確認しており、APIキー未設定環境のため実通信テストはしていません。

## 10. 将来の改善案（現行実装では未対応）

- 長時間残った `generating` runを安全に検出・回収する仕組み。回収条件・再試行可否・費用二重発生リスクを決めてから実装する。
- OpenAI APIの新しい推奨エンドポイントやモデル別のStructured Outputs互換性を、公式仕様で確認して選択可能にする。
- モデル出力の根拠日を機械検証する、または記録値との引用対応を持たせる。現状はプロンプト指示と文字列形式の検証のみ。
- 保存済み結果を消去する設定・保持期間を用意する。現状、同意撤回は新規送信の停止であり、run履歴の消去ではない。
- 手動再分析回数・利用額の見積りや追加上限を設ける。現状は実行前確認のみで、アプリ内の回数・金額上限はない。
- OSキーチェーンを使った暗号化保管や、OSバックアップからの除外。現在は権限を制限した平文JSONファイルへの保存です。
